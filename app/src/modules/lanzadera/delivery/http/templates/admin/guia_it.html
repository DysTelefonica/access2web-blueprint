Citrix, Linux y coexistencia

Dos lanzaderas, un entorno de ensayo aislado y un posible PostgreSQL común. La producción actual no se modifica.

Qué debe dejar listo IT hoy

Prepare capacidad, red, perfiles y almacenamiento aislados para que desarrollo ensaye con copias. Registre responsables, nombres y pruebas pendientes, y entregue el traspaso exportado.

Preparado ≠ validado. La {{ t("coexistencia", "coexistencia") }} es una propuesta de viabilidad, no una autorización de migración. No ejecute el {{ t("traslado", "traslado") }} de producción durante el aprovisionamiento. {{ t("hipotesis", "H-3 (perfil) y H-4 (anexos)") }} siguen sin demostrar.

  1. Confirme licencias de {{ t("citrix", "Citrix") }}, {{ t("multisesion", "Windows multisesión") }}, Access o {{ t("runtime", "Access Runtime") }} y el controlador {{ t("odbc", "ODBC") }}; dominio ({{ t("ad", "AD") }}), {{ t("dns", "DNS") }}, {{ t("ca", "certificados") }}, hora y permisos.
  2. Dimensione con IT las sesiones concurrentes, CPU, RAM y disco, y mida después en un ensayo multisesión. Esta guía no fija capacidad.
  3. Separe producción, {{ t("preproduccion", "preproducción") }} y desarrollo en bases, almacenamiento, cuentas, DNS y permisos. Las copias no envían correos ni ejecutan tareas programadas sin aprobación expresa.
  4. Reciba de desarrollo el artefacto de despliegue y el plan de pruebas; el {% call t("docker") %}docker-compose.yml{% endcall %} local no es una receta de producción.

01 · Servidor Windows y Citrix

  1. Prepare Windows multisesión y la publicación Citrix con dominio, DNS, hora sincronizada, licencias y acceso al recurso SMB. Pruebe con cuentas de prueba separadas antes de incorporar usuarios.
  2. Instale Access o Access Runtime compatible con los ACCDE desplegados. La arquitectura ({{ t("bitness", "bitness x86/x64") }}) de Office o Runtime, de los {{ t("accde", "ACCDE") }} y del controlador {{ t("psqlodbc", "psqlODBC") }} Unicode debe coincidir con lo instalado: compruébela, no la suponga.
  3. Publique la Lanzadera Access y el navegador corporativo como recursos distintos. Autorice ACCDE solo desde rutas aprobadas, sin desactivar la {{ t("macros", "protección de macros") }} de forma general.
  4. Configure un {{ t("perfil", "perfil persistente") }} por usuario con {{ t("upm", "Citrix UPM") }} o {{ t("upm", "FSLogix") }}, según elija y valide IT; no los combine sin probarlo. Conserve completa la carpeta {% call t("appdata") %}%APPDATA%\Aplicaciones DYSN\<NombreCarpetaTemporal>{% endcall %}, con permisos privados, tras el cierre de sesión, el reinicio del host y el cambio de {{ t("vda", "VDA") }}. No la sustituya por {% call t("temp") %}%TEMP%{% endcall %} ni por {% call t("temp") %}%LOCALAPPDATA%{% endcall %} sin adaptar y probar el código.

Cómo funciona hoy: ParaLanzadera.accdb copia la {{ t("lanzadera", "Lanzadera") }} a la carpeta del usuario. Si la versión publicada en el {% call t("ini") %}.ini{% endcall %} sube, se copian el {{ t("front", "front") }} y los iconos a esa carpeta del perfil y se ejecuta el front privado. Por eso la copia y su versión deben sobrevivir juntas entre sesiones: así la Lanzadera compara la última versión que el usuario tiene con la que ofrece.

02 · Linux, web y PostgreSQL

  1. Reserve una máquina Linux en la misma red con cuentas de servicio mínimas, DNS y certificados; separe los datos persistentes del sistema y dimensione el disco según el crecimiento medido.
  2. Prepare {{ t("postgresql", "PostgreSQL") }} con volumen duradero y cuentas de mínimo privilegio por entorno, acceso restringido por red y {{ t("tls", "TLS") }} con verificación del nombre. Acuerde {{ t("rpo", "RPO y RTO") }}, {{ t("offline", "copias fuera de línea") }} en otro host, retención y una prueba de restauración; {{ t("pitr", "PITR") }} si se provisiona y se prueba. Una copia sin restauración ensayada no cuenta como copia.
  3. Prepare un {{ t("proxy", "proxy") }} {{ t("https", "HTTPS") }} y el servicio de aplicación interno. No hay todavía un procedimiento verificado de proxy ni de copias de producción en el repositorio.
  4. Pida a desarrollo un manifiesto de despliegue revisado: {{ t("digest", "imagen fijada por digest") }}, nombres de {{ t("variables", "variables de entorno") }} sin valores, {{ t("migraciones", "migraciones") }} y su orden, {{ t("health", "sondas de salud") }}, usuario de servicio, volúmenes y política de proxy confiable. /health indica que la aplicación responde; no prueba datos ni conectividad completa. Los secretos se suministran desde el almacén aprobado, nunca en esta guía, en registros ni en argumentos.
  5. Acuerde el acceso de Linux a {% call t("anexos") %}ANEXOS{% endcall %} con {{ t("acl", "ACL") }} y cuentas mínimas, sin escritura para todos ni almacenamiento temporal. H-4 requiere ensayo y decisión.

{{ t("d93", "D93") }}: el {{ t("esquema", "esquema") }} <app>_legacy guarda las tablas compartidas con Access y <app> las que solo usa la web. Lo legacy no depende de lo web y no hay sincronización entre copias. Cualquier reversión web sigue un plan revisado que protege los datos compartidos; esta guía no incluye borrados de esquema.

03 · Ensayo y diagnóstico

Con copias aisladas y los cambios de acceso entregados por desarrollo, ensaye todas las aplicaciones y backends: identidad y permisos actuales, vínculos actualizables, lecturas y escrituras, concurrencia, consultas y documentos. Compruebe la separación de entornos y que el correo y los procesos en segundo plano siguen desactivados hasta su aprobación.

Ensaye también el cambio de botón entre lanzaderas y su reversión; esa reversión no devuelve los datos a ACCDB. Ante un fallo, detenga el cambio, conserve la evidencia y aplique el plan de recuperación aprobado.
