**Qué.** Un 503 transitorio de la API de GitHub dejaba en rojo un gate gobernado (ardelperal/APAP_WEB, 2026-11-12): el reintento agotó sus 3 intentos en unos 3 s (run 43244045339) y `pr-gate` falló al primer 503 al leer el cuerpo del PR (job 131271799279).
**Causa.** El reintento (#1210, #1220) esperaba 1 s fijo entre 3 intentos y reintentaba también los 4xx, que no son transitorios. Las escrituras del merge gobernado (`PUT .../merge`, `PATCH` de cierre) no reintentaban. `assets/issue-spec/check_issue_spec.py` llamaba a `urlopen` por su cuenta, con un único intento.
**Arreglo.** La regla de `assets/gh-api-retry/casos.tsv` reintenta un error de red, un 5xx, un 429 y un JSON malformado con backoff exponencial: 4 intentos con esperas de 2, 4 y 8 s (`GH_API_RETRY_ESPERA_S` es la primera espera y cada reintento la dobla). Un 4xx distinto de 429 y un fallo de configuración no se reintentan. Casos nuevos: `5xx-transitorio`, `4xx-no-reintenta`, `429-se-reintenta` y `backoff`; `github_rest.py` y `gh-api-retry.sh` recorren la tabla y observan las esperas sin dormir. `github_rest.call_con_reintento` aplica la regla a una escritura idempotente: el merge gobernado lo usa para el `PUT .../merge` con `sha`, el `PATCH` que cierra una issue, la consulta GraphQL y la relectura de la issue. El `POST` de un comentario, de una issue de incidente o de un `workflow_dispatch` hace un solo intento: repetido tras un 5xx que sí se aplicó, duplicaría el efecto. `check_issue_spec.py` (job `pr-gate`) carga `runner-controls/github_rest.py` por ruta (sin él sale con 2) y lee el PR y las issues con `github_rest.con_reintento`; el texto de un 4xx no cambia. Tests: `test_governed_merge_retry.py`, `IdempotentWriteRetryTests` en `test_github_rest_retry.py` y `PrEventApiRetryTests` en `test_check_issue_spec.py`.
**A partir de ahora.** Una ráfaga de 5xx de hasta unos 14 s ya no deja un gate en rojo; un 4xx falla al primer intento.
