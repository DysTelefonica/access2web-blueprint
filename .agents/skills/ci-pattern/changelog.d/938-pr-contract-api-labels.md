El gate de contrato de PR (`assets/pr-contract/check_pr_contract.py`) añade un modo vivo opt-in que lee `pull_request.labels` y `pull_request.body` desde la API de GitHub (`GET /repos/{r}/issues/{n}/labels` y `GET /repos/{r}/pulls/{n}`) en lugar de la instantánea del evento ($GITHUB_EVENT_PATH), siguiendo el precedent cerrado de #830/#831 para `issue-spec` (#938). El modo vivo es opt-in: solo se activa si el caller setea `PR_CONTRACT_USE_LIVE_API=1` y `GITHUB_TOKEN` en el entorno; sin opt-in, el gate sigue leyendo labels y body del payload, que es el contrato del modo local, del propagador y de los tests del catálogo, que invocan el gate como subproceso sin token. Bajo opt-in, sin token o con la API caída, el gate falla cerrado (exit 2) con motivo explícito. El catálogo delega el cliente REST y la excepción fail-closed a `runner-controls/github_rest.py`, que se carga por ruta con el mismo patrón que `check_docs_architecture` (mismo manejo para consumers con pin y vendorizados). Suite de tests: 5 nuevos casos en `assets/pr-contract/tests/test_pr_contract.py` (4 del modo vivo con mock server local; 1 que fija el modo por defecto: el gate lee del payload sin token ni opt-in).
