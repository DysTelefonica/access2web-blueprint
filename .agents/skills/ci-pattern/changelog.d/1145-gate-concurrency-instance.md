El gate `workflow-policy` compara ahora los workflows analizados entre sí y exige que un gate con dos instancias separe su cola por instancia. El mismo job puede correr en dos instancias: su workflow con disparador propio (`pull_request`) y el mismo fichero invocado con `workflow_call` desde otro workflow. Con el mismo grupo de concurrencia, GitHub guarda una sola petición pendiente por grupo y cancela la pendiente cuando llega otra: la instancia llamada se canceló a los 0 s («Canceling since a higher priority waiting request for gate-pr-gate-1371 exists») y el agregador `required` leyó `cancelled` como fallo, dejando el pull request rojo sin defecto (DysTelefonica/access2web-blueprint#1371, run `ci` 40084048493 intento 1). El grupo separa las instancias cuando nombra `github.run_id`, o `github.workflow` si las instancias toman nombres distintos (dentro de un reusable `github.workflow` es el del caller), o un `inputs.<x>` que cada caller rellene con un valor no vacío y distinto; la otra salida es una sola instancia. `cancel-in-progress: false` se mantiene. Sin prueba de la segunda instancia (el reusable fuera de los `--workflow` analizados) no se reporta nada. Los consumers con un gate dual sin discriminante verán un hallazgo nuevo al propagarse (#1145, HR-73).
