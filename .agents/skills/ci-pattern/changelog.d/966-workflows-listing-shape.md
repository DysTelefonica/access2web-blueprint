#966: `check_governed_merge.py` (asset vendorizado del merge gobernado) deja de rechazar el listado de workflows que devuelve `GET /repos/<repo>/actions/workflows`. La API responde un objeto `{"total_count": N, "workflows": [...]}`, no una lista, y la validación de `post_merge_dispatch` exigía la lista: todo consumer que declarara esa clave en su `host-contract.json` veía el merge bloqueado con `workflows listing is not the API shape: dict` (observado en cadete en el run de `governed-merge.yml` del PR #573). El gate recorre ahora todas las páginas con `per_page=100` y `page` mientras la página venga llena, de modo que un repo con más de 30 workflows —o con más de 100— no da un falso «no existe». El fail-closed se mantiene: sin la clave `workflows`, o con un valor que no sea lista, el merge se bloquea nombrando la forma esperada (`{"total_count": N, "workflows": [...]}`). Los dobles de los tests (`tests/_github_stub.py`) sirven ya la forma real y la paginación, con un test que fija la forma antigua (lista desnuda) como bloqueante y otro que cubre el workflow declarado en la segunda página. Sin cambios en el contrato del host, sin secretos nuevos: el token del job sigue siendo el único permiso en juego.
