Merge gobernado (#817, punta de cadena): `check_governed_merge.py` dispara **tras el merge** — y solo si este sale bien — por `workflow_dispatch` los workflows cuyo basename aparezca en la clave opcional `post_merge_dispatch` del `host-contract.json` del consumer, en el orden declarado y sobre la rama base del PR. El disparo usa el mismo `GITHUB_TOKEN` del job — `workflow_dispatch` sí crea ejecuciones con ese token, mientras que `on: push` queda suprimida por contrato de GitHub Actions; por eso, antes de este fix, los merges gobernados de `ardelperal/APAP_WEB` y `DysTelefonica/cadete` salían sin `deploy`, sin `runner-detective`, sin `runner-guard`, sin `ci`, sin `push-compliance`, sin `force-push-guard` y sin el detective post-push corriendo sobre el SHA fusionado (verificado en los últimos 5 commits `github-actions[bot]` de cada `main` por `gh api /actions/runs?head_sha=<sha>`: `total_count` del propio `runner-merge`/`governed-merge` y cero runs con `event=push`). El eslabón previo (`817-post-merge-dispatch.md`) ya validaba los nombres pre-merge; este los dispara. Cada llamada es `POST /repos/<repo>/actions/workflows/<wf>/dispatches` con `{"ref": <rama base del PR>}` (204 si OK): esa API solo acepta una rama o una etiqueta en `ref` y responde 422 a un SHA. Los 4xx/5xx se acumulan y elevan a un único exit 4 con el nombre del (o los) workflow(s) fallado(s); el merge ya está hecho y **no** se deshace (idempotencia hacia atrás, HR-34). El permiso `actions: write` necesario en el workflow del consumer se documenta en el PR de adopción, fuera de este cambio. Sin secretos nuevos, App ni PAT: `workflow_dispatch` no está entre los eventos suprimidos por `GITHUB_TOKEN`, así que el mismo token del job basta para re-disparar cada workflow declarado.

Closes #817
