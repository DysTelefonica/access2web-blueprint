HR-7 (#1056) también mira los mensajes de commit, no solo el cuerpo del PR. GitHub cierra una issue por las palabras clave que encuentre en cualquiera de los dos sitios, y el gate solo leía el cuerpo: un PR con `chain:partial` cuyo cuerpo decía `Refs #1035` y cuyo commit decía `(Closes #1035)` cerraba la issue en cuanto se mergeaba, con la cadena abierta. Pasó dos veces: el PR 1050 cerró la issue 1035 con la fricción (c) sin resolver (el timeline la registra cerrada por `commit_id: 27d6817d` a los cinco segundos del merge, y el mantenedor la reabrió) y el PR 1037 cerró la 1033 a medias. Ahora `check_pr_contract.py` falla con HR-7 cuando el PR lleva la etiqueta de intermedio y algún commit del rango contiene una de las nueve palabras clave de GitHub seguidas de `#N` (`close`, `closes`, `closed`, `fix`, `fixes`, `fixed`, `resolve`, `resolves`, `resolved`, sin distinguir mayúsculas); el hallazgo nombra el commit por su subject y propone `Refs #N` con el número que el propio commit cita. Un «close» sin número no cierra nada y no dispara nada, y el PR punta de cadena sigue pudiendo llevar `Closes` en sus commits, que es justo lo que HR-7 le pide. El texto juzgado es el mismo `--commits-file` que ya generaba el workflow para HR-14 con merge-base desde #1013: ni una llamada nueva a la API ni git dentro del gate, y la comprobación cuelga de la clave `commits` que la política ya tiene, así que el contrato `checks` no crece. Tests: el caso del PR 1050 en rojo y el del PR punta en verde, más las nueve palabras clave en sus tres formas y el negativo sin `#N`.

Pendiente fuera de este cambio: el texto de HR-7 en este mismo `SKILL.md` sigue prohibiendo las palabras de cierre solo en el título, y el archivo está en 999 líneas con el máximo estricto de HR-2 en 1000. Añadirlo a la prosa del canon exige pagar la línea condensando otra regla que esta issue no autorizó, así que la regla nueva queda registrada aquí y en el hallazgo del gate; ampliar HR-7 en el canon es un follow-up aparte.
