El fragmento canónico del job `governance-seals` mide el gate UNA vez, con `--config-from base` y la base como suelo: el PR puede AÑADIR y no puede QUITAR (DysTelefonica/team-skills#1339). Antes llevaba dos invocaciones (`--config-from base` y `--seal-baseline base`) y su combinación ponía en rojo un PR legítimo: el que gobierna con el contrato de la base no puede conocer el artefacto de gobierno que el PR acaba de crear (E9), y medir dos veces con dos reglas no es medir más. Con `--config-from <dir>` el contrato que gobierna el gate sale de `<dir>` (la base del PR, sin credenciales) y el estado que se mide sigue siendo el del repo; lo que el PR declara de más se mide con la unión de la base y la cabeza —el inventario de la fase 0 y las rutas gobernadas declaradas por unión, con la base mandando en el conflicto, y los `pattern_paths` de la fase 3 son los que declara el PR— y el suelo de sellado de la base se conserva: lo que la base sellaba no se reduce en un PR mientras el fichero siga en el árbol (E8b). Retirar un workflow sí se permite: si el fichero ya no existe, no hay nada que sellar.
