type: patch

**Qué.** La política de workflows (#978) rechazaba `cancel-in-progress: ${{ github.ref != 'refs/heads/main' }}` en un workflow con `pull_request`, y `safe_merge` seguía juzgando el check-run de cada nombre con el `id` más alto, de modo que un gemelo `cancelled` más reciente bloqueaba una PR en verde.
**Causa.** #978 solo admitía `false` o una expresión sobre `synchronize`, porque un run cancelado del mismo SHA dejaba un check `cancelled` que bloqueaba el merge. #1591 arregló esa lectura en el merge gobernado (`check_push_compliance._latest_by_name`), pero `safe_merge.ci_findings` conservaba la regla antigua.
**Arreglo.** `safe_merge.ci_findings` reutiliza `_latest_by_name`: por cada nombre decide el check-run más reciente **no cancelado**; si todos están cancelados, decide el cancelado más reciente y el merge se bloquea. Con ambos gates así, `cancel_in_progress_findings` admite también una expresión sobre `github.ref` (no `github.ref_name`); el `true` literal y cualquier otra expresión siguen siendo hallazgo. Tests: `test_an_expression_on_the_ref_passes`, `test_a_job_level_expression_on_the_ref_passes`, `test_the_finding_names_the_ref_way_out`, `test_old_run_cancelled_by_the_new_one_merges_when_the_new_one_is_green`, `test_newer_cancelled_twin_of_a_green_run_merges`, `test_cancelled_alone_is_denied`, `test_all_twins_cancelled_is_denied` y `test_newer_cancelled_twin_does_not_hide_an_older_failure`.
**A partir de ahora.** En un workflow con `pull_request`, `cancel-in-progress` puede ser `false`, una expresión sobre `synchronize` o una expresión sobre `github.ref`. Un `cancelled` solo es veredicto en `safe_merge` cuando no hay otro check-run del mismo nombre sobre el mismo SHA.
