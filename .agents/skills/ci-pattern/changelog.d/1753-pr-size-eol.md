**Qué.** La medida local del presupuesto (`assets/pr-size/check_pr_size.py`) cuenta como la API de GitHub y como A1: ya no normaliza los finales de línea antes de contar. Y cuando parte de las líneas contadas solo cambian el final de línea, la herramienta lo dice en voz alta: `N lineas son solo finales de linea: revisa la conversion de EOL`, con `N` medido comparando la cuenta real con la cuenta que ignora el EOL. El sobre JSON suma el indicador `eol_only_lines` y, cuando hay ruido, el campo `notice`.
**Causa.** La bandera `--ignore-cr-at-eol` venía del gate del harness (`515a0a3e`), con la razón de que el ruido de finales de línea no es trabajo de revisión; la puerta del harness la quitó después para contar como GitHub (`819d2ea0`: «cuenta adiciones mas eliminaciones tal como las da GitHub, sin normalizar CRLF»), pero al portar el script a `ci-pattern` volvió con su razón vieja (`116bf0d1`, #623). De ahí la divergencia: la misma PR medía 308 líneas en local y 716 en CI (APAP #4153), y el worker se enteraba del desvío por el rojo de CI, no por la herramienta que mide (#1753).
**Arreglo.** Se cuenta sin normalizar, igual que A1 y que la API, y el aviso nombra solo las líneas que son ruido de EOL. El veredicto, las opciones y los códigos de salida no cambian: el aviso informa, no decide.
**A partir de ahora.** La cifra local y la de CI coinciden, también cuando hay conversión de finales de línea.

Migración: quien mida el presupuesto con `assets/pr-size/check_pr_size.py` ve ahora la misma cifra que A1 y que la API de GitHub (los finales de línea ya no se normalizan) y, cuando parte de las líneas contadas solo cambian el final de línea, un aviso `WARN` con el número de esas líneas; si algún flujo esperaba la cuenta que ignoraba el EOL, revise esa expectativa. El sobre JSON suma `indicators.eol_only_lines` y, solo cuando hay ruido, `notice`.
