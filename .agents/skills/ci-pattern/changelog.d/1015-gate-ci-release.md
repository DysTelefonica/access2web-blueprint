#1015 (punto 1): `assets/release-gate/check_release_ci.py` cierra el hueco que el gate del tag no cubría — el workflow de release y el de CI son independientes, así que un tag podía publicar con el CI en rojo sobre los bytes que se firman. El gate resuelve con `git` el commit del tag, pregunta al host los runs del workflow de CI (`--workflow`, por defecto `ci.yml`) para ese `head_sha`, toma el más nuevo (desempata por fecha de creación y luego por el ID inmutable, porque el orden de la API no es un contrato) y exige `completed` + `success`. Sin ningún run para ese SHA sale 2 —no dice nada sobre un sujeto que no midió—, igual que una API caída o un tag inexistente; con runs que no termina en `success` sale 1. La suite usa un doble del cliente de la API y un repositorio git temporal, sin red.
