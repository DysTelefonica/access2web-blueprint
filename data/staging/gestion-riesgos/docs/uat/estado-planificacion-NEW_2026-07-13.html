Como se prueba en staging

  1. Abrir Form_FormRiesgosGestion, seleccionar una edicion con un riesgo que tenga plan de mitigacion o contingencia.
  2. Escenario (a) violada: crear accion con FechaFinPrevista anterior a FechaInicio. Esperado: MsgBox + Cancel (edicion) o Raise 1000 (alta). El valor NO se persiste.
  3. Escenario (a) igualdad: FechaFinPrevista = FechaInicio. Esperado: acepta sin error.
  4. Escenario (b) violada: FechaInicio anterior a la fecha de creacion de la primera edicion del proyecto. Esperado: MsgBox + Cancel. El valor NO se persiste.
  5. Escenario (b) satisfecha: FechaInicio >= MIN(FechaEdicion) del proyecto. Esperado: acepta sin error.
  6. Sin FechaInicio: dejar el campo vacio. Esperado: constraint (a) no aplica, no rechaza.
  7. Regression: ejecutar tests.vba.accion-fechas-helper.json (8 atomos) + Test_RiesgoFechasHelper (4) + Test_RiesgoMaterializacion (16). Esperado: 28/28 verde.

5. Riesgos y notas

  • codegraph-vba v1.7.0 round-5 prompt criteria diverges de la implementacion real: el prompt del maintainer en docs/prompts/prompt-ia-mantenedora-codegraph-vba-round-5-2026-07-13.md esperaba stub_true_count < 500, pero la shipped implementacion mantiene el count y agrega repointDecision (declined-runtime / declined-not-found / declined-ambiguous). Filed como ardelperal/codegraph-vba#115 para que el maintainer archive o actualice el prompt.
  • Dysflow daemon no respawnea tras kill: al matar el daemon de staging (necesario para liberar el lock del DB en un reindex forzado), no se levanta automaticamente uno nuevo. MCP queries funcionan via DB directa, pero el file-watcher incremental queda caido hasta que el usuario corra codegraph-vba sync <project> o reinicie el MCP server. Filed como ardelperal/codegraph-vba#116.
  • Dysflow test_vba allowlist gate (PR1b): el gate es nuevo. Cualquier test nuevo creado sin agregar al .dysflow/project.json capabilities.procedures.allow fallara con PROCEDURE_NOT_ALLOWED. Workflow post-creacion: agregar al allowlist antes de test_vba.
  • Dysflow test_vba filter bug: el parametro filter del tool dysflow.test_vba no encuentra procedures que SI estan en el allowlist. Workaround actual: usar proceduresJson con lista explicita. Anotado feedback al maintainer del adapter v2.1.7.
  • Cache-first en Form_FormPlanAcciones (alta): m_FechaBaseProyecto se resuelve en Form_Load. Si el usuario crea multiples acciones seguidas en el mismo form load, el cache es valido (mismo proyecto, misma primera edicion). Si reabre el form para otra accion de otro proyecto, se re-resuelve. Edge case raro pero documentado.
