Citrix, Linux y coexistencia

Guía de preparación para IT · 19 de noviembre de 2026

Dos lanzaderas, un entorno de ensayo aislado y un posible PostgreSQL común. La producción actual no se modifica hoy.

Qué debe dejar listo IT hoy

Prepare capacidad, red, perfiles y almacenamiento aislados para que desarrollo pueda ensayar con copias. Registre responsables, nombres y pruebas pendientes; entregue esta guía junto con el archivo de traspaso exportado.

Preparado ≠ validado. La coexistencia es una propuesta de viabilidad, no una autorización de migración. No ejecute el traslado de producción durante el aprovisionamiento. H-3 (perfil) y H-4 (anexos) siguen sin demostrar.

  1. Confirme licencias Citrix, Windows/RDS, Access o Runtime y controlador; dominio AD, DNS, certificados, hora, red y permisos.
  2. Dimensione inicialmente sesiones concurrentes, CPU, RAM y disco con IT; mida después en un ensayo multisesión. Ninguna cifra aquí es capacidad garantizada.
  3. Separe producción, preproducción y desarrollo en bases, almacenamiento, cuentas, DNS y permisos. Las copias no deben alcanzar producción ni emitir correos o tareas programadas sin aprobación expresa.
  4. Reciba de desarrollo el artefacto de despliegue y el plan de pruebas; no convierta el compose local en producción.

Arquitectura por escenario

Seleccione un escenario para destacarlo. Sin JavaScript se muestran todos; al imprimir se incluyen todos.

01 · Producción actual

La Lanzadera Access abre únicamente aplicaciones Access. Los backends por aplicación, ANEXOS y recursos (.accde, .ini, iconos) están en \\datoste\APLICACIONES_DYS\Aplicaciones PpD\. No cambiar esta ruta ni los datos de producción para el ensayo.

02 · Ensayo aislado

Citrix Windows publica la Lanzadera Access y un navegador; una máquina Linux de la misma red aloja web y PostgreSQL de ensayo. Use URL, recursos SMB, bases, almacenamiento y cuentas de preproducción distintos de los reales. Las copias se reciben mediante el procedimiento aprobado; no se conectan a producción.

03 · Coexistencia propuesta, después de aprobación

El usuario entra por Citrix: Access abre solo aplicaciones legacy y el navegador publicado abre solo las nuevas aplicaciones web. Ambas usan los datos compartidos en PostgreSQL; no hay sincronización de dos copias. Tras la convivencia, se prevé OpenShift. Las URL y rutas futuras deben ser distintas de las de ensayo y acordadas por IT.

Secuencia propuesta: saneamiento aprobado del legacy y adaptación de acceso; ensayo de todos los backends sobre PostgreSQL; decisión y traslado único autorizado de todos los datos de producción; después, cambio de interfaz por aplicación. El botón puede volver a Access, pero no revierte el traslado de datos, considerado irreversible.

Flujos que IT debe autorizar

Restringir por origen, destino y entorno; resolver nombres y certificados antes de probar. Puertos indicados son destinos, no una orden para abrirlos indiscriminadamente.

PostgreSQL nunca se expone a los puestos de usuario ni a Internet. El Dockerfile actual confía por defecto en todos los proxies: producción debe restringir explícitamente las cabeceras reenviadas al proxy real y bloquear el acceso directo al puerto de aplicación.

01 · Servidor Windows y Citrix

  1. Prepare Windows multisesión y publicación Citrix con AD, DNS, hora sincronizada, licencias y acceso al recurso SMB. Compruebe con cuentas de prueba separadas antes de incorporar usuarios.
  2. Instale Access o Access Runtime compatible con los ACCDE desplegados. La arquitectura x86/x64 del Runtime/Office, los ACCDE y el controlador Unicode psqlODBC debe coincidir con lo realmente instalado; no suponga bitness.
  3. Publique la Lanzadera Access y el navegador corporativo como recursos distintos. Autorice la ejecución de ACCDE solo desde rutas aprobadas; no desactive las protecciones de macros de forma general.
  4. Configure un perfil persistente por usuario con Citrix UPM o FSLogix según elección y validación de IT; no configure ambos a ciegas. Preserve la carpeta completa y metadatos de versión en %APPDATA%\Aplicaciones DYSN\<NombreCarpetaTemporal>, con permisos privados. Debe conservarse tras cierre de sesión, reinicio del host y cambio de VDA. No sustituya por %TEMP% ni %LOCALAPPDATA% sin adaptar y probar el código.

Cómo funciona hoy: ParaLanzadera.accdb copia la Lanzadera por usuario. Cuando sube la versión publicada en el .ini, se copian front e iconos a esa ruta del perfil y se ejecuta el front privado. La versión local debe persistir coherentemente junto a los archivos.

H-3 está pendiente: valide dos usuarios aislados; el mismo usuario en otro VDA reutiliza caché; versión igual no recopia y versión nueva actualiza; cierre y reapertura, reinicio y actualización con aplicación abierta. Simule caída de red: no debe haber escrituras obsoletas ni sobrescritura parcial. Registre resultados y corrija con desarrollo si falla.

La conexión ODBC no convierte automáticamente VBA, SQL ni vínculos: desarrollo debe adaptar las aperturas y revinculación de cada front/backend, claves y consultas, y validar lecturas, escrituras y concurrencia en copias antes de cualquier corte.

02 · Linux, web y PostgreSQL

  1. Reserve una máquina Linux en la misma red con cuentas de servicio mínimas, DNS y certificados; separe datos persistentes del sistema y dimensione disco según crecimiento medido.
  2. Prepare PostgreSQL con volumen duradero y cuentas por entorno de mínimo privilegio. Controle acceso por red y TLS con verificación del nombre. Acordar RPO/RTO, copias fuera de línea en otro host, retención y prueba de restauración; prever PITR si se ha provisionado y probado. No considerar válida una copia sin ensayo de restauración.
  3. Prepare proxy HTTPS y servicio de aplicación interno. docker-compose.yml es exclusivamente desarrollo local: no es un manifiesto de producción ni una receta que se pueda copiar. No hay aquí un runbook de proxy o backup de producción verificado.
  4. Solicite a desarrollo un manifiesto de producción revisado: imagen fijada por digest, nombres de variables de entorno sin valores secretos, migraciones y orden de ejecución, probes de salud, usuario de servicio, volúmenes y política de proxy confiable. El endpoint documentado /health es una señal de aplicación, no prueba de datos ni de conectividad completa. El MVP usa adaptador de secretos por entorno; IT debe decidir su suministro desde almacén aprobado sin incluir valores en esta guía, logs ni argumentos.
  5. Acuerde acceso de Linux a ANEXOS con ACL y cuentas mínimas, sin escritura mundial ni almacenamiento temporal. H-4 (compartir los documentos legacy con la web) requiere ensayo y decisión; no presuponga que ya funciona.

Durante la coexistencia, D93 reserva <app>_legacy para tablas compartidas y <app> para tablas solo web. No debe haber dependencias desde legacy hacia web. No hay sincronización entre copias. La reversión web requiere un plan revisado que proteja los datos compartidos; no ejecutar borrados de esquema desde esta guía.

03 · Ensayo y diagnóstico

Con copias aisladas y cambios de acceso entregados por desarrollo, ensaye todas las aplicaciones y backends: identidad y permisos existentes, vínculos actualizables, operaciones de lectura/escritura, concurrencia, consultas SQL y documentos. Verifique separación de entornos y que correo y procesos en segundo plano están deshabilitados hasta aprobación. Mantenga la autorización de aplicaciones existente.

Registre prueba, entorno, fecha, resultado y responsable. La habilitación de una aplicación web y deshabilitación de su botón Access se ensayan junto con su reversión; esto no devuelve los datos a ACCDB. Ante un fallo, detenga el cambio, conserve evidencia y aplique el plan aprobado de recuperación; no improvise migraciones.

Comprobaciones de solo lectura

Ejemplos: sustituya los marcadores por nombres no secretos aprobados. Ejecutar desde el host indicado; no proporcionan por sí solos prueba funcional ni deben incluir credenciales.

nslookup <nombre-dns-del-entorno>
Test-NetConnection <servidor-postgresql-del-entorno> -Port 5432

El segundo ejemplo comprueba solo conectividad TCP desde Windows, no TLS ni autorización. Si copiar falla, seleccione el texto y cópielo manualmente.

Diagnóstico: DNS o hora incorrectos pueden invalidar certificados; TCP abierto no demuestra autenticación; compruebe el nombre del certificado y la CA sin desactivar verify-full. Ante error de perfil, compare usuario, VDA, ruta resuelta y versión; ante error de anexos, revise montaje y ACL sin exponer documentos.

Glosario

Cada término subrayado de la guía enlaza aquí. Use «Atrás» en el navegador para volver al punto de lectura.

ACCDB y ACCDE
Formatos de archivo de Access. ACCDB es editable; ACCDE es la versión compilada que se entrega a los usuarios, sin código modificable. Un ACCDE solo abre en un Access de su misma bitness.
Access Runtime
Versión gratuita de Access que ejecuta aplicaciones pero no permite editarlas; evita instalar Office completo en el servidor.
ACL
Lista de permisos de una carpeta o archivo: quién puede leer, quién escribir y quién no tiene acceso.
Active Directory (AD)
Directorio corporativo de usuarios, grupos y equipos. Da el inicio de sesión y los permisos de red.
ANEXOS
Carpeta de cada aplicación con los documentos adjuntos guardados como archivos.
%APPDATA%
Carpeta del perfil del usuario (Roaming) que viaja con el perfil. La Lanzadera guarda aquí la copia del front y su versión.
Archivo .ini de versión
Archivo de texto junto al front publicado que indica su versión. La Lanzadera lo compara con la versión de la copia local del usuario para decidir si copia el front nuevo.
Backend
Archivo Access que guarda las tablas con los datos; lo comparten todos los usuarios de la aplicación.
Bitness (x86 / x64)
Si un programa es de 32 bits (x86) o de 64 bits (x64). Access u Office, los ACCDE y el controlador ODBC tienen que ser de la misma: un Access de 32 bits solo ve controladores ODBC de 32 bits, y un ACCDE compilado en 32 bits no abre en un Access de 64 bits (ni al revés). Se consulta en Access, en Archivo › Cuenta › Acerca de Access.
CA y certificado
Un certificado acredita la identidad de un servidor; la CA (autoridad de certificación) es quien lo firma. La validación falla si el nombre del servidor o la hora del equipo no cuadran.
Cabeceras reenviadas
Datos que el proxy añade a cada petición (IP original, protocolo). La aplicación solo debe creerlas si vienen del proxy real; si no, cualquiera podría falsearlas.
Citrix
Plataforma que ejecuta las aplicaciones en servidores centrales y muestra la pantalla al usuario. El puesto solo necesita el cliente Citrix.
Citrix UPM y FSLogix
Dos formas de conservar los perfiles de usuario en Citrix. UPM copia las carpetas del perfil al entrar y al salir; FSLogix monta el perfil completo desde un disco virtual. Se elige una de las dos.
Coexistencia
Periodo en que conviven la Lanzadera Access y la web sobre los mismos datos. Cada aplicación está en un solo lado a la vez.
Contenedor, Docker y docker-compose
Un contenedor empaqueta una aplicación con todo lo que necesita para ejecutarse. docker-compose arranca varios contenedores juntos; el del repositorio es solo para desarrollo, no para producción.
Copia fuera de línea
Copia guardada en otra máquina, sin acceso desde el servidor original, para que sobreviva a un borrado o a un ataque.
D93
Decisión de arquitectura: cada aplicación tiene en PostgreSQL un esquema <app>_legacy con las tablas compartidas con Access y otro <app> con lo que añade la web.
DNS
Servicio que traduce nombres de servidor a direcciones IP. Los certificados se validan contra el nombre, no contra la IP.
Esquema
Agrupación de tablas dentro de una base de datos PostgreSQL, parecida a una carpeta.
Front
Parte de una aplicación Access que ve el usuario: formularios e informes. Cada usuario ejecuta su propia copia.
H-3 y H-4
Hipótesis pendientes de ensayo. H-3: la copia del front por usuario funciona en Citrix. H-4: cómo accede la web a los ANEXOS.
HTTPS (puerto 443)
Acceso web cifrado con TLS.
Imagen fijada por digest
La imagen es el paquete de un contenedor; el digest es su huella única (sha256:…). Fijarlo garantiza desplegar exactamente lo revisado.
JSON de traspaso
Archivo de texto con las marcas y notas de la lista de entrega, para llevarlas a otro equipo o adjuntarlas a la incidencia.
Lanzadera
Aplicación de entrada que muestra a cada usuario las aplicaciones a las que tiene permiso. La de Access abre aplicaciones Access; la web, solo aplicaciones web.
Migraciones
Scripts versionados que crean o cambian las tablas de la base de datos, aplicados en orden.
ODBC
Estándar de Windows para que un programa, aquí Access, se conecte a una base de datos externa mediante un controlador.
OpenShift
Plataforma corporativa de contenedores a la que se prevé llevar la web al terminar la convivencia.
Perfil persistente
Carpeta con la configuración y los archivos de cada usuario que se guarda al cerrar sesión y se recupera al entrar, en cualquier VDA.
PITR
Recuperación de la base de datos a un instante concreto, combinando una copia con el registro de cambios de PostgreSQL.
PostgreSQL
Base de datos que sustituirá a los backends Access; la usarán a la vez Access, mediante ODBC, y la web.
Preproducción o ensayo
Entorno con copias de producción para probar sin riesgo; nunca toca datos reales.
Protección de macros
Seguridad de Office que bloquea código VBA de origen no confiable. Se autorizan rutas concretas (ubicaciones de confianza) en lugar de desactivarla.
Proxy inverso
Servidor web situado delante de la aplicación: recibe el HTTPS y reenvía las peticiones al puerto interno, de modo que la aplicación no queda expuesta.
psqlODBC
Controlador ODBC oficial de PostgreSQL. Se usa la variante Unicode, que trata bien acentos y eñes, y de la misma bitness que Access.
Puerto TCP
Número que identifica un servicio en una máquina: 443 web, 5432 PostgreSQL, 445 carpetas compartidas. Abrirlo solo a orígenes concretos limita quién puede conectarse.
RPO y RTO
RPO: cuántos datos se pueden perder como máximo (por ejemplo, la última hora). RTO: cuánto puede tardar la recuperación.
SMB (puerto 445)
Protocolo de Windows para carpetas compartidas en red, como \\datoste\APLICACIONES_DYS.
Sonda de salud (/health)
Dirección que responde si la aplicación está en marcha. No prueba que los datos ni las conexiones funcionen.
%TEMP% y %LOCALAPPDATA%
Carpetas locales de la máquina: normalmente no viajan con el perfil y pueden vaciarse al cerrar sesión. Por eso no sirven para la copia de la Lanzadera.
TLS
Cifrado de las conexiones de red; impide leer o alterar el tráfico.
Traslado único
Paso de todos los datos de Access a PostgreSQL de una sola vez en producción. Es irreversible.
Uvicorn (puerto 8000)
Servidor que ejecuta la aplicación web Python dentro del contenedor. Ese puerto solo debe ser accesible desde el proxy.
Variables de entorno y secretos
Configuración que recibe la aplicación al arrancar. Los secretos (contraseñas, claves) llegan desde un almacén aprobado y nunca se escriben en documentos ni registros.
VDA
Máquina Windows donde Citrix ejecuta las sesiones. Hay varias, y un usuario puede entrar cada día en una distinta.
verify-full
Modo de conexión de PostgreSQL que cifra con TLS y además comprueba que el certificado lo firma una CA de confianza y corresponde al nombre del servidor. Evita suplantaciones.
Windows multisesión (RDS)
Windows Server configurado para que varios usuarios trabajen a la vez en la misma máquina.
