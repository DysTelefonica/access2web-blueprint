Propuesta en exploración · Épica #1545

Prueba de viabilidad: ¿pueden convivir Access y la web sobre los mismos datos?

El plan actual es un cambio único al final: cuando la última aplicación web esté terminada, se apaga todo Access y se enciende lo nuevo. Estamos explorando si es posible otra vía: pasar primero todos los datos a PostgreSQL, tras un ensayo completo, y después llevar las aplicaciones a la web una a una, de forma que cada una pueda volver a Access si hace falta.

Dos caminos

Plan actual

Corte único al final

La web se construye aparte, sin compartir nada con Access. Cuando la última aplicación web está terminada, se apaga todo el legacy y se enciende lo nuevo de una vez.

  • Nada se pone en producción hasta el final.
  • Todo el riesgo se concentra en un solo día.
  • Los datos se migran de golpe en ese corte.
Propuesta en exploración

Coexistencia, aplicación a aplicación

Primero todos los datos pasan de los ficheros Access a PostgreSQL, y las aplicaciones Access siguen funcionando contra él. Después cada aplicación pasa a la web cuando está lista, y volver atrás es encender de nuevo su botón en Access.

  • Los datos se mueven una sola vez, tras un ensayo completo en Citrix. Ese paso no tiene vuelta atrás.
  • Cada aplicación entra en servicio en cuanto está lista.
  • El paso de cada aplicación a la web sí se puede deshacer.
Qué tiene que demostrar la exploración. Que todas las aplicaciones Access funcionan en Citrix contra PostgreSQL, sin backends Access, y con un rendimiento aceptable. Se demuestra en preproducción antes del traslado de los datos, que es el único paso sin vuelta atrás. Si no se demuestra, se sigue con el corte único, y el inventario de la fase 0 sirve igual para ese camino.

Cómo funciona hoy y cómo quedaría con la propuesta

Cada aplicación se copia al ordenador de cada usuario y se ejecuta allí. Los datos viven en ficheros Access en una unidad de red compartida.

Ordenador de cada usuario

Todo lo que sigue ocurre en cada puesto, uno por uno

  1. El usuario pulsa el acceso directo, que abre ParaLanzadera.accdb en la unidad de red.
  2. Se copia la última versión de la Lanzadera a la carpeta temporal del usuario y se abre en su equipo.
  3. Al abrir cada aplicación, si la versión de su .ini ha subido, se copian a su equipo el front compilado (.accde) y sus iconos desde la carpeta recursos.
  4. La aplicación se ejecuta en el equipo del usuario y lee y escribe directamente en el fichero de datos de su carpeta, y en ANEXOS los documentos.

Una carpeta por aplicación

En la unidad de red compartida. Dentro: recursos (front, versión e iconos), el fichero de datos y ANEXOS.

Con la propuesta, las aplicaciones Access dejarían de copiarse a cada equipo: se ejecutarían en un servidor. Pulse una aplicación para cambiarla de máquina. Así funcionaría cada corte, y la vuelta atrás sería la misma operación. Es una demostración: el orden real lo fijaría el mapa de dependencias.
