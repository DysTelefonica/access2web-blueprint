De qué va, en una frase: hay once aplicaciones de Access, cada una con su propia base de datos. Vamos a pasarlas a la web sin perder ni un dato, y lo hacemos por dentro primero: dejar las bases de datos limpias y ordenadas, y solo después moverlas.

La regla que lo ordena todo: primero se limpia, después se mueve. Ningún dato pasa a la nueva base de datos hasta que las once aplicaciones estén limpias.

1 · Cómo está hoy

Cada aplicación es un programa y tiene su propio cajón de datos (un archivo .accdb con tablas dentro). Cuando una aplicación necesita datos de otra, no los copia: abre el cajón de la otra con un vínculo. Por eso hay bases de datos que varias aplicaciones comparten.

2 · Qué es el saneamiento (limpiar antes de mover)

Antes de llevar los datos a la nueva base de datos, los limpiamos en su sitio. Es arreglo de casa antes de una mudanza: si movemos el desorden, lo movemos dos veces.

3 · Quién hace qué y cuándo

El saneamiento va en paralelo: cada bloque limpia lo suyo, y cuando uno termina, el otro nos dice qué se queda y qué no. Entonces modificamos y retiramos lo que ya no se use.

4 · Cómo va a quedar

Una sola fuente de verdad. Las aplicaciones de Access que no se apagan siguen trabajando con los mismos datos, ahora en la base nueva, y la web usa esas mismas tablas.

5 · Qué pasa en los primeros seis meses

Las once aplicaciones del alcance. En estos seis meses todas se limpian (se ordenan sus datos en Access); las dos marcadas tienen además desarrollo de la versión web.

Las palabras que se usan en estos documentos, explicadas

Aplicación (o front). El programa que usa una persona: el que ve en pantalla.

Base de datos (o backend). El cajón donde están los datos de una aplicación, un archivo .accdb de Access.

Tabla. Una lista de datos con filas (cada cosa) y columnas (cada dato).

Vínculo. Acceso de una base de datos a los datos de otra, sin copiarlos.

Clave primaria. La columna que dice qué fila es cada una, sin repeticiones. Sin ella la fila no se puede modificar.

Tabla huérfana. Una tabla que ya no usa ninguna aplicación.

Cuarentena. Apartar lo que no se usa renombrándolo. No se borra: se puede volver atrás.

Esquema. La zona de PostgreSQL que pertenece a una aplicación, para que no se mezclen sus datos.

ODBC. El puente con el que Access se conecta a PostgreSQL sin cambiar el programa.

Corte. Pasar una aplicación de Access a su versión web.

Coexistencia. Las dos versiones vivas a la vez, con vuelta atrás en un botón.

Bloque A y bloque B. Primero la cola de correo (bloque A, toca a todas las aplicaciones) y luego aplicación por aplicación (bloque B).

Revisión de requisitos. La tarea de la jefatura funcional: decir de cada aplicación y de cada funcionalidad qué se usa y qué no, para poder retirarlo o mantenerlo. Es la parte en la que nos tiene que responder.

UAT. Pruebas con usuarios reales antes de dar algo por bueno.

Citrix. El sistema por el que se entra a las aplicaciones: desde el puesto solo se necesita el cliente.

El corte a la web de cada aplicación va DESPUÉS de mayo, con el traslado único de los datos: es el único paso sin vuelta atrás. Hasta entonces, la web se desarrolla y se prueba en paralelo, pero sin hitos de uso real. El resto: el proyecto · en dos páginas · los seis meses · monográfico · migración · portal
